## 1. Solo PostgreSQL, sin ORM

- **Conexión:** `lib/db.ts` exporta `pool` (un `pg.Pool` con `connectionTimeoutMillis: 5000` y listener de `error`) y `dbQuery()`. Lee `POSTGRES_URL` o `DATABASE_URL`.
- **No hay Drizzle, Prisma ni Knex.** Las consultas son SQL a mano, parametrizadas (`$1, $2...`).
- **No agregues otro motor** (SQLite, MySQL, MongoDB, `pg-mem`, PGlite), tampoco para pruebas.

## 2. Dónde vive el esquema

**`lib/db-schema.ts` es la única fuente del DDL.** Cada tabla tiene su `ensureXTable()`, y `ensureCoreSchema()` las llama todas en orden de dependencias. Son idempotentes (`CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`).

**Corre una sola vez, al arrancar el servidor:** `instrumentation.ts` llama a `ensureCoreSchema()` antes de atender peticiones. Si falta `DATABASE_URL`/`POSTGRES_URL`, termina de inmediato en producción (es un error de configuración, reintentar no sirve). Si Postgres no responde, reintenta 30 veces cada 2 s; si sigue sin responder, en producción termina el proceso para que Docker lo reinicie. No se ejecuta durante `next build`. **No llames `ensure*()` en rutas ni acciones.** El usuario de la base necesita permisos de DDL al arrancar.

**No hay migraciones versionadas.** Para cambiar el esquema:

1. **Columna nueva:** agrégala al `CREATE TABLE` (para instalaciones nuevas) **y** como `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` (para bases existentes).
2. **Cambios no idempotentes** (restricciones, `DROP NOT NULL`, CHECK): envuélvelos para que repetirlos no falle. Por ejemplo, `DO $$ ... IF NOT EXISTS (SELECT 1 FROM pg_constraint ...) ... $$` como en `campana_supervisores`.
3. **Renombrar o borrar columnas:** coméntalo con el equipo antes de hacerlo. El patrón que se usó el 2026-10-30 para pasar columnas a tablas propias: crear la tabla nueva y, dentro de un `DO $$ ... IF EXISTS (SELECT 1 FROM information_schema.columns WHERE table_name = ... AND column_name = ...) THEN` copiar los datos y hacer `DROP COLUMN`. Así la migración corre una sola vez y una base vacía nace ya con el esquema nuevo. Va en orden de dependencias dentro de `ensureCoreSchema()` (la tabla de origen, antes). Al escribir SQL con `$$` desde un script de Node, no uses `String.replace(a, b)` con texto fijo: `$$` se vuelve `$`; usa una función de reemplazo.
4. **`sql/*.sql` son scripts viejos** que ya no coinciden con `db-schema.ts`. No los uses como referencia ni los actualices.

## 4. Convenciones

- **Nombres:** tablas y columnas en snake_case. Mezclan español (`campanas`, `usuarios`, `motivo`) e inglés (`status`, `created_at`, `campaign_id`). Sigue lo que ya usa la tabla que tocas.
- **Claves:** `SERIAL`. Los IDs llegan al frontend como `string`.
- **Estados:** `VARCHAR` con valores en español (`borrador`, `en_revision`, `aceptada`, `activa`, `finalizada`...; `pendiente`, `aceptado`, `rechazado`...). Revisa `types/index.ts` antes de agregar uno.
- **Contadores desnormalizados** en `campana_estadisticas` (y `enviados` en `campana_tipos`): si insertas, cambias de estado o borras un aporte, recalcúlalos **en la misma transacción** con `recalcularContadores` (ver `app/api/aportes/[id]/route.ts`).
- **Fragmentos de lectura (2026-10-30):** lo que salió de `campanas`, `aportes` y `usuarios` a tablas propias se lee con fragmentos SQL que lo devuelven con los nombres de antes: `columnasCalculadas("c")`, `columnasDeArchivo("a")`, `columnaDeRespuestas("a")`, `columnaDeRoles("u")`. Ponlos en todo `SELECT`/`RETURNING` cuya fila llegue a una pantalla o a un `map*` de `types/index.ts`. Para filtrar, `condicionDeTipos` y `condicionDeRol`; **nunca** `role @>` ni `data_types ?` (esas columnas ya no existen).
- **Llaves foráneas con índice:** Postgres no lo crea solo. Toda FK nueva lleva su `CREATE INDEX IF NOT EXISTS`, o agrégala a `INDICES_DE_LLAVES` (`ensureIndicesDeLlaves()`, 2026-10-30) si no la cubre otro índice que empiece por esa columna.
- **Índice de la cifra "Participantes" de la landing (2026-11-03):** `aportes_participante_aprobado_idx`, sobre `COALESCE(user_id::text, anonimo_id)` con `WHERE status = 'aceptado'`. Para que Postgres lo use, la expresión y la condición de `obtenerCifras()` (`app/page.tsx`) deben ser **idénticas**: si cambias una, cambia la otra.
- **Reglas CHECK de estados y tipos** (`ensureRestricciones()`, 2026-10-30): estados de campaña y aporte, `collection_mode`, `pausa_por`, `proposito`, `calificacion` (1 a 5, `ESTRELLAS_MAXIMAS`), `reportes.estado`/`origen`, `sanciones.tipo`, `avatar`, `baja_destino_aportes`. Las listas salen de las constantes del código (`PROPOSITOS`, `TIPOS_DE_SANCION`, `DESTINOS_DE_APORTES`) y se quitan y vuelven a poner en cada arranque (`NOT VALID` + `VALIDATE`; si una fila vieja no cumple, avisa con WARNING y la app arranca). **Un valor nuevo de estado o tipo va en la constante o en `restricciones()`**, o la base lo rechaza.
- **Carreras:** resuélvelas con un `UPDATE ... WHERE <condición> RETURNING` y revisa `rowCount` (ejemplo: tomar una campaña en `lib/supervision/decision.ts`).
- **Transición perezosa de estados:** `activateScheduledCampaigns()` y `finalizeExpiredCampaigns()` (`lib/campaign-date.ts`) pasan `aceptada → activa` y `activa → finalizada` cada minuto (tarea de `instrumentation-node.ts`, desde el 2026-10-16) y al leer `/api/campanas`, `/explorar`, la landing y la portada de `/sistema`. No hay cron.

## 5. JSONB

Desde el 2026-10-30 quedan pocas columnas JSONB: `usuarios.intereses`, `campana_tipos.formatos`, `notificaciones.metadata`, `audit_log.detalle` y `medallas.criterio`, además de las de gamificación (`parametros_gamificacion.valores`, `misiones.condicion` y `recompensa`, `racha_eventos.detalle`...). Roles, tipos de dato, checklists y respuestas pasaron a tablas (ver § 3); los fragmentos de lectura los siguen devolviendo como JSONB para no cambiar las pantallas. Para filtrar un JSONB usa `@>` o `?`. Si algo necesita relaciones, contadores, filtros o historial, va en tabla propia.

## 6. Fechas y zonas horarias

- **Todo instante es `TIMESTAMPTZ`.** El 2026-10-30, `ensureFechasConZona()` pasó a `TIMESTAMPTZ` las últimas columnas `TIMESTAMP` sin zona (`created_at`/`updated_at` de varias tablas, `aportes.submitted_at`, `aportes.reviewed_at`...) con `USING col AT TIME ZONE 'UTC'`. La lista está en `COLUMNAS_CON_ZONA`; una columna nueva de instante nace `TIMESTAMPTZ`.
- **Fechas de campaña:** `DATE` + `TIME` por separado. Se interpretan con `lib/campaign-date.ts` (`normalizeCampaignDate`, `hasCampaignStarted`, `hasCampaignEnded`).
  - Son **hora de pared de Tepic** (`ZONA_DE_CAMPANAS = "America/Mazatlan"`). "Ahora" y "hoy" se calculan en esa zona con `Intl`, **nunca con la zona del proceso ni con `NOW()`**: dentro de Docker los dos son UTC. Hasta el 2026-10-07 se usaba la hora local del proceso y una campaña de 15:00 a 20:00 aceptada a mediodía se finalizaba al instante (en UTC ya eran más de las 20:00). Para "hoy" en cualquier otro cálculo, usa la misma zona.
  - Las gráficas de aportes por día de `lib/campanas/panel.ts` y `/api/campanas/[id]/recoleccion-diaria` cuentan los días en hora de Tepic desde el 2026-10-28: el día se saca con `to_char(submitted_at AT TIME ZONE $3, 'YYYY-MM-DD')` con `$3 = ZONA_DE_CAMPANAS` (un solo `AT TIME ZONE`: con `TIMESTAMPTZ`, el doble `AT TIME ZONE 'UTC'` de antes desfasaba el día; se quitó en 8 consultas el 2026-10-30) y la lista de días sale de `hoyEnTepic()` (antes, desde las 17:00 de Tepic contaban el día siguiente).
